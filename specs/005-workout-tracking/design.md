## Approach

The workout feature is a thin client-state layer (`ActiveWorkoutScreen` + a handful of bottom sheets/overlays) over a small, session/set-shaped REST API. All server-authoritative logging happens through two endpoints — `POST /workouts/sessions/{id}/sets` and `POST /workouts/sessions/{id}/finish` — regardless of whether a set's data came from manual keypad entry or from a camera-coached live-tracking pass. The camera-coached flow is deliberately kept out of the write path: `LiveTrackingOverlay` never calls the repository; it only returns a `LiveSetResult` that prefills the same editable `_SetEntry` row the manual flow uses, so "LOG SET" is the single place a set is actually persisted (`presentation/widgets/live_tracking_overlay.dart:16-19`, `presentation/active_workout_screen.dart:324`). This keeps PR detection, XP, and achievement evaluation entirely server-side and flow-agnostic.

State is Riverpod `FutureProvider`s keyed by session id (`workout_providers.dart`) plus one small cross-screen handoff (`pendingCameraCoachProvider`) used because the app router's `/workout/active/:sessionId` route doesn't thread `GoRouterState.extra` (`workout_providers.dart:33-51`).

## Architecture / Data Flow

### Trace 1 — Manual set-logging flow

1. `CoachEntryScreen._startWorkout` (`presentation/coach_entry_screen.dart:23`) loads the active program, offers `showStartWorkoutSheet` (program day vs. freestyle), then calls `WorkoutRepository.startSession(programDayId, label)` → `POST /workouts/sessions` → `workouts.py:start_session` creates a `WorkoutSession` row and returns it via `WorkoutSessionRead`.
2. `context.push(AppRoutes.workoutActive(session.id))` opens `ActiveWorkoutScreen(sessionId)` (`presentation/active_workout_screen.dart:89`), which watches `sessionProvider(sessionId)` (a `FutureProvider.family`, `workout_providers.dart:28-31`).
3. On first load, `_initializePlan` (`active_workout_screen.dart:125-216`) builds the in-memory `_PlanExercise`/`_SetEntry` grid: if `session.programDayId != null`, it resolves the matching `ProgramDay` from `_activeProgramProvider` and seeds one `_SetEntry` per prescribed set (target reps/weight from `ProgramExercise`); otherwise it seeds a freestyle plan from whatever sets are already logged, in first-appearance order. Already-logged `WorkoutSet`s from the session are then merged back into the matching rows.
4. Tapping a set row opens `showSetEntrySheet` (`presentation/widgets/set_entry_sheet.dart`) — a keypad-driven weight/reps editor with NORMAL/WARM-UP/DROP toggle and, for barbell exercises (`equipment.contains('barbell')`), a live `computePlateBreakdown` label (`plate_math.dart:38`). Its result only updates local `_SetEntry` state; nothing is sent to the server yet.
5. Tapping "LOG SET" runs `_logCurrentSet` (`active_workout_screen.dart:324-437`), which calls `WorkoutRepository.logSet(...)` → `POST /workouts/sessions/{id}/sets` → `workouts.py:log_set`: looks up the `Exercise`, inserts a `WorkoutSet`, flushes (to get its id), then calls `maybe_record_pr` (`services/records.py:19-54`) before committing.
6. Back on the client, the row is marked `logged`; if `loggedSet.isPr`, `showPrCelebration` (`presentation/widgets/pr_celebration_overlay.dart`) is awaited first (using the best prior set found client-side across the last 20 sessions), then `showPostSetSummarySheet` (`presentation/widgets/post_set_summary_sheet.dart`) shows reps/depth/form plus an optional "vs last time" comparison against the same set index from the most recent other finished session sharing the same label.
7. If that was the workout's final set (last row of the last exercise), `_finishWorkout` (`active_workout_screen.dart:439-452`) calls `WorkoutRepository.finishSession` → `POST /workouts/sessions/{id}/finish` → `workouts.py:finish_session` (stamps `ended_at`/`duration_s`, averages `form_score`, awards XP, calls `evaluate_achievements`) and navigates to `AppRoutes.workoutSummary(sessionId)`. Otherwise, `showRestTimerSheet` (`presentation/widgets/rest_timer_sheet.dart`) runs a local countdown (default `user.restTimerDefaultS` or 90s) before returning control.
8. `WorkoutSummaryScreen` (`presentation/workout_summary_screen.dart`) re-fetches the finished session, shows stat tiles (duration/volume/sets/reps/calories/avg form, with deltas vs. the last same-label finished session), a PR banner, an exercise breakdown, a muscles-trained diagram, and RPE/mood/notes inputs that each re-call `finishSession` on change (`_submit`, lines 77-97).
9. `WorkoutHistoryScreen` (`presentation/workout_history_screen.dart`) separately fetches up to 200 sessions via `workoutHistoryProvider` and renders a client-side calendar heatmap (`_CalendarCard`) plus a month-grouped list (`_SessionRow`), both derived from `WorkoutSession.sets` with no server-side date filtering.

### Trace 2 — Camera-coached flow (start → precheck → live tracking → post-set summary)

1. From `ActiveWorkoutScreen`, when the current `_PlanExercise.supportsCoaching` is true (`coachWithCamera` from the program, or `exercise.supportsCamera`), the bottom bar shows a "COACH SET" button wired to `_openCameraPrecheck` (`active_workout_screen.dart:454-457`, `_BottomActionBar`), which pushes `AppRoutes.workoutCameraPrecheck(sessionId, programExerciseId: plan.programExerciseId)`.
2. `CameraPrecheckScreen` (`presentation/camera_precheck_screen.dart`) constructs its own `PoseCoachService` (module 006, `camera_coach/data/pose_service.dart`) and calls `initialize()`/`startStream(...)`. Each incoming `Pose` is run through the local `_evaluate` heuristic (`camera_precheck_screen.dart:36-78`) to drive a live checklist: full body in frame, side view detected, too close, lighting good — all approximate proxies documented inline.
3. If permission is denied or no camera exists, the screen shows a fallback with a "KEEP LOGGING MANUALLY" / "OPEN SETTINGS" action that calls `_leave()` and returns to the active-workout screen without ever entering live tracking (`camera_precheck_screen.dart:182-220`).
4. Tapping "I'M READY" runs `_confirmAndContinue` (`camera_precheck_screen.dart:167-174`): it sets `pendingCameraCoachProvider.notifier.state = sessionId` (module-level handoff, `workout_providers.dart:33-51`) and calls `_leave()` to pop back to `ActiveWorkoutScreen`.
5. `ActiveWorkoutScreen._buildScaffold` (`active_workout_screen.dart:578-591`) reads `pendingCameraCoachProvider`; when it matches the current session and there's a current plan exercise, it renders `LiveTrackingOverlay` full-screen instead of the normal set-table UI, passing `exercise`, `voiceCoachSettings` (from `AuthController`'s user), `onFinish: _handleLiveSetFinished`, `onCancel: _handleLiveTrackingCancel`.
6. `LiveTrackingOverlay` (`presentation/widgets/live_tracking_overlay.dart`) wires together the full module 006 engine: its own `PoseCoachService` instance, `VoiceCoach`, a `RepCounter` (configured via `repCounterConfigFor(inferMovementPattern(...))`, `presentation/widgets/pose_angle_mapper.dart:127-150`), and `FormHeuristics`. Each pose frame is converted to camera-agnostic `JointAngles` by `jointAnglesFromPose` (`presentation/widgets/pose_angle_mapper.dart:80-111`) — this is this module's one integration/bridge point into the engine's pure-domain types — then fed to both `FormHeuristics.evaluateFrame`/`addSample` and `RepCounter.addSample`. `PoseSkeletonPainter` (`presentation/widgets/pose_painter.dart`) draws the live skeleton overlay, coloring bones red where `FormSnapshot` flags that joint group. Rep completions and cues drive `VoiceCoach.announceRep`/`speak`/`speakEncouragement`.
7. Tapping "FINISH SET" runs `_finish` (`live_tracking_overlay.dart:165-178`): stops the pose stream and calls `widget.onFinish(LiveSetResult(reps, formScore, romPct, goodReps, badReps, dominantFlaggedJoint))` — no API call happens here.
8. Back in `ActiveWorkoutScreen`, `_handleLiveSetFinished` (`active_workout_screen.dart:459-476`) clears the pending-camera-coach state and writes the result's fields onto the current (still-unlogged) `_SetEntry` row (`reps` only overwritten if `>0`; `formScoreHint`, `romHint`, `goodRepsHint`, `badRepsHint`, `flaggedJointHint` always set). The UI falls back to the normal set-table view, now prefilled.
9. The lifter still taps "LOG SET" to actually submit — this re-enters Trace 1 step 5 exactly, now with `formScore`/`depthPct` populated from the camera pass. `_coachingNoteFor` (`active_workout_screen.dart:305-322`) prefers an exercise-authored `Exercise.mistakes` entry matching the `flaggedJointHint`'s keywords over a generic score/depth threshold message, for both the post-set summary's "ONE THING TO FIX" banner and the rest timer's "FROM YOUR LAST SET" note.
10. Canceling out of live tracking (`onCancel` → `_handleLiveTrackingCancel`, `active_workout_screen.dart:478-481`) or backing out of the precheck screen both clear `pendingCameraCoachProvider` and return to the manual set row unchanged — no partial camera data is written.
11. Later, `FormReportScreen` (`presentation/form_report_screen.dart`) reads back whichever sets in the finished session have `formScore`/`depthPct` set (i.e., were camera-coached) and renders a per-exercise form-score trend, depth-by-rep bars, and templated "what came up" cues (`_whatCameUp`, lines 385-419) — entirely derived from `WorkoutSet` fields, no separate rep-by-rep store.

## Data / Schema

Backend (`backend/app/models/workout.py`):
- `WorkoutSession`: `id`, `user_id` (FK `users.id`), `program_day_id` (FK `program_days.id`, nullable — null means freestyle), `label`, `started_at` (server default now), `ended_at` (null while active), `duration_s`, `calories`, `avg_form_score`, `rpe`, `mood` (1-5), `notes`; `sets` relationship with `cascade="all, delete-orphan"`, ordered by `WorkoutSet.set_index`.
- `WorkoutSet`: `id`, `session_id` (FK), `exercise_id` (FK `exercises.id`), `set_index`, `set_type` (`normal`/`warmup`/`drop`), `target_weight_kg`, `target_reps`, `actual_weight_kg`, `actual_reps`, `rpe`, `form_score` (0-100, comment: "from on-device coaching"), `depth_pct`, `is_pr` (default false), `completed_at`.

Schemas (`backend/app/schemas/workout.py`): `WorkoutSetCreate`/`WorkoutSetRead`, `WorkoutSessionCreate`/`WorkoutSessionFinish`/`WorkoutSessionRead` mirror the models; `WorkoutSetRead` nests a full `ExerciseRead`.

Client domain (`app/lib/features/workout/domain/workout_session.dart`): `WorkoutSet` and `WorkoutSession` are straight `fromJson` mirrors of the above, plus a computed `WorkoutSession.isFinished => endedAt != null`.

Client-only, not persisted: `_PlanExercise` and `_SetEntry` (`presentation/active_workout_screen.dart:34-77`) — the on-screen plan grid, merged from program data (or freestyle) and already-logged `WorkoutSet`s, plus live-tracking hints (`formScoreHint`, `romHint`, `goodRepsHint`, `badRepsHint`, `flaggedJointHint`) that exist only until the row is logged. `LiveSetResult` (`presentation/widgets/live_tracking_overlay.dart:20-46`) is the hand-off DTO between the camera engine and this module; it is never itself sent to the backend — its fields ride along inside the next `logSet` call.

`PersonalRecord` (`backend/app/models/record.py`, read by `services/records.py` but owned by a different module) stores `weight_kg`, `reps`, `est_1rm_kg`, `workout_set_id` per user/exercise; `maybe_record_pr` only reads/writes this table and the `is_pr` flag on the just-inserted `WorkoutSet`.

## Testing Strategy

No automated tests exist for this module — gap. `app/test/widget_test.dart` is a single unrelated smoke test (verifies the signed-out app renders the login screen) and does not touch any workout screen, provider, or repository. `backend/` has no `tests/` directory at all (only third-party test suites under `backend/.venv/lib/...`); `workouts.py`, `services/records.py`, and the plate-math/pose-angle-mapper pure functions in this module have zero unit or integration coverage.

## Risks / Edge Cases

- **Camera controller double-dispose guard (`CameraPrecheckScreen`)**: the screen tracks a `_leaving` flag (`presentation/camera_precheck_screen.dart:106`) that is set the instant teardown starts, on every exit path. The documented reason (comment, lines 96-105) is that `CameraController.dispose()` posts a value-change notification that `CameraPreview`'s `ValueListenableBuilder` can still be subscribed to for one more frame, and without the guard a stray rebuild in that window calls `buildPreview()` on an already-disposed controller and throws `CameraException(Disposed CameraController, ...)`. The implementation is: `_leave()` (explicit close/skip/ready paths) sets `_leaving = true` before awaiting `_poseService.dispose()`, and while `_leaving` is true `build()` short-circuits to a loading spinner instead of touching `CameraPreview` (line 178); `dispose()`'s fallback (for exits that skip `_leave()`, e.g. a system back-swipe) only calls `_poseService.dispose()` if `_leaving` is still false, and disposal is itself idempotent ("no-ops once `_controller` is already null" per the comment at line 150). This is a currently-complete protective mechanism, not an open gap, as implemented.
- **`LiveTrackingOverlay` has no equivalent `_leaving`-style guard**, but it disposes unconditionally in `dispose()` (`live_tracking_overlay.dart:192-196`) and has no separate "leave" path with an async gap before pop — `onCancel`/`onFinish` are synchronous callbacks into the parent, so the same race window doesn't arise the same way.
- **PR "previous best" lookup is bounded, not exhaustive**: both the client's pre-celebration lookup (`active_workout_screen.dart:380-392`, scans `sessionListProvider`'s most recent 20 sessions) and the "vs last time" comparisons in the post-set summary and form report are explicitly scoped to recent history only; the code comments acknowledge this can under-report a genuinely older best rather than fabricate a comparison (`active_workout_screen.dart:381-383`).
- **Freestyle set-count inference**: when rebuilding a freestyle plan from already-logged sets, the set count for an exercise is derived as `max(setIndex) + 1` (`active_workout_screen.dart:169`), so a gap in `set_index` (e.g. from a deleted middle set) would understate/misalign the row count; there is no explicit handling for non-contiguous indices.
- **Rest-timer negative-duration guard**: `_total` is floored to `1` when `initialSeconds <= 0` to avoid a divide-by-zero in the progress calculation (`rest_timer_sheet.dart:39`).
- **Plate math leftover**: non-standard target weights (e.g. a typed-in odd number) can leave a `leftoverPerSideKg` that the standard plate set can't represent exactly; this is documented as expected behavior, not a bug (`plate_math.dart:11-14,23-26`).

## Backlog / Known Gaps

- No automated tests anywhere in this module (see Testing Strategy) — the most significant gap found.
- Per-set RPE is modeled end-to-end in the schema/model (`WorkoutSetCreate.rpe`, `WorkoutSet.rpe`) but `_logCurrentSet` never populates it (`active_workout_screen.dart:333-346` omits an `rpe:` argument) — only session-level RPE (via the summary screen) is actually reachable from the UI today.
- `programExerciseId` is threaded from `ActiveWorkoutScreen` through `CameraPrecheckScreen` and into the route (`_openCameraPrecheck`, `active_workout_screen.dart:454-457`) but is not read anywhere in `CameraPrecheckScreen`'s body beyond being accepted as a constructor field; the code comment at `camera_precheck_screen.dart:168-171` states this is intentional, "threaded through purely so a future backend integration can log which prescribed exercise this coached set belongs to" — a documented, not-yet-wired hook rather than a bug.
