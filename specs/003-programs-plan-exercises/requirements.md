## Summary

This module covers the core training-plan domain: `Program` / `ProgramDay` / `ProgramExercise`, the curated `Exercise` catalog/library, and the two ways a program gets its exercises populated — a deterministic rule-based generator (`backend/app/services/plan_generator.py`) and an AI-personalized generator (`backend/app/services/ai_plan_generator.py`) that layers LLM-driven exercise selection on top of the same deterministic day skeleton and silently falls back to the deterministic path on any failure. It also covers the day-editor UI (rename day, add/remove muscle tags, add/remove/reorder exercises, edit set/rep/load targets, "fill day") and the exercise library/detail screens.

## Background / Problem

A user coming out of onboarding needs a structured weekly training program without having to build one exercise-by-exercise. FORMA solves this with a rule-based split/day/exercise generator that is always available, optionally enhanced by an LLM (Groq-hosted `openai/gpt-oss-120b`) that personalizes exercise selection, set/rep schemes, tempo, and supersets per day — while guaranteeing the AI path can never leave the user without a program if the LLM call fails, times out, returns malformed/truncated JSON, references an invalid exercise, or violates a hard injury-safety rule. Once a program exists, the user can browse/filter FORMA's own curated exercise library and hand-edit any part of their plan.

## User Stories

- As a new user finishing onboarding, I want a complete weekly program generated from my goal, experience, days/week, session length, equipment, and injuries, so I don't have to build a plan from scratch.
- As a user, I want to regenerate my whole plan (e.g. from the plan overview's "Regenerate plan" menu or onboarding's plan preview) using the same or updated quiz answers.
- As a user, I want to rename a training day and adjust which muscle groups it targets.
- As a user, I want to add, remove, and reorder exercises within a day, and edit each exercise's sets, rep range, load type/target, tempo, notes, and camera-coaching flag.
- As a user, I want a one-tap way to auto-populate a day with more exercises that fit its existing muscle tags and my equipment.
- As a user, I want to search and filter FORMA's exercise library (by name, muscle, equipment, camera-coaching support) and view a body-map picker, so I can find exercises to add.
- As a user, I want to view full exercise detail (execution steps, pro cues, common mistakes, my personal history, similar alternatives) before adding it or doing it standalone.
- As a user with a tagged injury, I want the plan generator to avoid exercises that load the injured area when I've flagged it as "avoid" severity.

## Acceptance Criteria (EARS format: "WHEN/IF ... THE SYSTEM SHALL ...")

- WHEN a client calls `POST /programs/generate` with no `days_per_week` in the request and none saved on the user's profile, THE SYSTEM SHALL respond `400 Bad Request`.
- WHEN `POST /programs/generate` succeeds, THE SYSTEM SHALL deactivate any previously-active program owned by the user before activating the newly generated one, so exactly one program is `is_active = true` at a time.
- IF `GROQ_API_KEY` is not configured, THEN `generate_program_smart` SHALL call the deterministic generator directly with no network call and no AI attempt.
- IF `GROQ_API_KEY` is configured, THEN `generate_program_smart` SHALL first attempt AI-driven generation (`generate_program_ai`); IF that call raises for any reason (Groq API error, schema-validation failure, day-count mismatch, day-label/order mismatch, unknown exercise slug, or a hard injury-avoidance violation), THEN THE SYSTEM SHALL roll back any partial writes, log a warning, and fall back to the deterministic generator (`plan_generator.generate_program`) so the request still succeeds.
- WHEN the AI generator produces a response whose `days` array length does not match the deterministic day-skeleton's length, THE SYSTEM SHALL treat it as invalid and raise (triggering fallback) rather than accept a partial or padded result.
- WHEN the AI generator selects an exercise for a day, THE SYSTEM SHALL reject (raise, triggering fallback) any selection whose primary muscles intersect an "avoid"-severity injury's mapped muscle set, regardless of what the prompt instructed.
- WHEN a program is generated by either path, THE SYSTEM SHALL tag it `source = "generated"` (deterministic) or `source = "ai_generated"` (AI-personalized) accordingly.
- WHEN a user renames a day or edits its muscle tags via the day editor, THE SYSTEM SHALL persist the change through `PATCH /programs/days/{day_id}` (the same generic day-update endpoint for both operations), not a dedicated rename/tag endpoint.
- WHEN a user taps "Let AI fill this day," THE SYSTEM SHALL call `POST /programs/days/{day_id}/fill`, which appends exercises chosen by the same deterministic heuristic (`select_exercises_for_day`) used by the non-AI plan generator — THE SYSTEM SHALL NOT make an LLM call for this action.
- WHEN "fill day" is invoked on a day already at or above its target exercise count for the user's session length, THE SYSTEM SHALL make no changes (no-op) and still return the day unchanged.
- WHEN "fill day" runs, THE SYSTEM SHALL only append exercises (never remove or replace existing ones on that day).
- WHEN a user adds an exercise to a day, updates a program-exercise's fields, or removes a program-exercise, THE SYSTEM SHALL verify the requesting user owns the parent program (via the day's program) before applying the change, returning `404` otherwise.
- WHEN `GET /exercises` is called, THE SYSTEM SHALL support optional `search` (case-insensitive substring on name), `muscle` (primary-muscle containment), and `equipment` (containment) filters, and cap `limit` at 100 regardless of the requested value.
- WHEN a client fetches a program, day, or exercise the requesting user does not own, THE SYSTEM SHALL respond `404 Not Found` (not `403`), for both programs and program days/exercises.
- IF no active program exists for the user, THEN `GET /programs/active` SHALL respond `404`, and the Flutter repository SHALL translate that specifically into a `null` result (not an error) for the UI's "no plan yet" state.

## Out of Scope

- Per-week programming variation: a program has one repeating week structure (`program.days`); there is no server-side concept of week-to-week progression, deload weeks, or a program start date. The Flutter plan-overview screen derives "week N" client-side from workout history as a display-only construct.
- Server-side validation of manually-edited set/rep/load bounds — the `ProgramExerciseCreate`/`ProgramExerciseUpdate` Pydantic schemas place no `ge`/`le` constraints on `sets`, `rep_range_low/high`, or `target_value` (unlike the AI-generation schema, which does constrain these).
- A dedicated "manual" program-creation flow — `Program.source` is documented in the Flutter domain model as `"generated | manual"`, but no code path in this module was found that ever writes `"manual"`.
- Adding an exercise to a plan directly from the exercise detail screen — its "ADD TO PLAN" button shows a snackbar telling the user to open a day instead; it performs no mutation.
- Exercise-catalog authoring/admin UI — the library is static seed data (`backend/app/db/seed_data.py`), not user- or admin-editable through any endpoint in this module.

## Non-Functional Requirements

- The AI generation path must never be the sole path to a successful `POST /programs/generate` response — a working deterministic fallback is a hard requirement, not best-effort, since onboarding depends on this endpoint succeeding.
- AI prompt/catalog payloads are sized to Groq's token-per-minute rate limits: the exercise catalog sent to the model is trimmed to `slug`/`name`/`primary_muscles`/`equipment` only and serialized compact (no pretty-printing), and `max_tokens` is computed per request (`ai_utils.max_tokens_for`) rather than left at an implicit default, per a documented prior truncation incident.
- All program/day/exercise-mutation endpoints require an authenticated user (`get_current_user`) and enforce per-resource ownership before reading or mutating.
- Exercise-library reads are effectively unpaginated in practice: the catalog is ~47 rows and the Flutter client always requests `limit: 100`, so the server-side `limit` cap (100) is never actually exercised by the shipped client.

## Open Questions

- Is `Program.source = "manual"` a planned-but-unbuilt value, or dead documentation left over from an earlier design? No code path producing it was found.
- Should the AI-vs-deterministic origin of a generated program (`Program.source`) be surfaced to the user anywhere? It is parsed into the Flutter `Program` model but not read or displayed by any screen in this module.
- Is the "✨ Let AI fill this day" button copy intentional marketing language for a heuristic feature, or should it be relabeled/reimplemented to match its deterministic implementation?
