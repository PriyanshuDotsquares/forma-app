## Approach

Three layers:

1. **Domain model** — `Program` has many `ProgramDay` (cascade delete-orphan), each `ProgramDay` has many `ProgramExercise` (cascade delete-orphan), each pointing at a shared `Exercise` catalog row. One `is_active` program per user at a time.
2. **Generation** — a single deterministic "skeleton builder" (`plan_generator._resolve_split` / `_build_day_plans`) decides the split type and each day's label/muscle-tags/weekday. Three things consume that skeleton: the pure-deterministic generator (also fills exercises via `select_exercises_for_day`), the AI generator (fills exercises via an LLM call constrained to that same skeleton), and the "fill day" feature (reuses `select_exercises_for_day` directly against an existing day). `ai_plan_generator.generate_program_smart` is the only entry point callers use for `/programs/generate`; it decides AI-vs-deterministic and owns the fallback.
3. **Manual editing** — day and program-exercise CRUD through plain REST endpoints; the Flutter day editor optimistically reorders in memory then persists via per-item PATCH calls, always re-fetching the full active program afterward through a single shared `ActiveProgramController` so the plan-overview and day-editor screens never drift out of sync.

## Architecture / Data Flow

### (a) Program generation — deterministic-vs-AI branch and fallback

Onboarding's own flow (module 002) collects the quiz answers and triggers the first generation from `app/lib/features/onboarding/presentation/steps/step9_building.dart` (initial call) and `plan_preview_screen.dart` (`_regenerate`, for retries/edits) — both call into this module rather than duplicating it; see module 002 for the onboarding-side UI. The call chain from that point on, and for the "Regenerate plan" action on `plan_overview_screen.dart`, is:

1. `ActiveProgramController.regenerate(...)` (`app/lib/features/programs/presentation/active_program_controller.dart:21`) sets `AsyncLoading` and calls the repository.
2. `ProgramsRepository.generateProgram(...)` (`app/lib/features/programs/data/programs_repository.dart:39`) does `POST /programs/generate` with `goal`, `experience_level`, `days_per_week`, `session_minutes`, `split_preference`, `equipment`, `injuries` — `injuries` is sent explicitly here (not read server-side off the saved profile) because during first-time onboarding this call happens before `PATCH /onboarding` persists it.
3. `programs.py generate()` (`backend/app/api/v1/endpoints/programs.py:54`) resolves each field to the request value or the user's saved profile, requires a resolved `days_per_week` (400 if none), and calls `generate_program_smart(db, user=..., ...)`.
4. `ai_plan_generator.generate_program_smart` (`backend/app/services/ai_plan_generator.py:308`):
   - IF `settings.groq_api_key` is falsy → calls `plan_generator.generate_program` directly (no network call at all).
   - ELSE → `try: return await generate_program_ai(...)`; `except Exception:` → `logger.warning(..., exc_info=True)`, `await db.rollback()` (discards any partial AI-path writes), re-fetches `user` with an awaited `db.get(User, user_id)` (a bare attribute access on the now-expired `user` object would crash with `MissingGreenlet`), then calls `plan_generator.generate_program` as the fallback. This `except Exception` is intentionally broad — it catches Groq API errors, Pydantic validation errors, and the module's own `ValueError`s (day-count mismatch, day-label/order mismatch, unknown exercise slug, injury-avoidance violation) uniformly.
5. `generate_program_ai` (`ai_plan_generator.py:169`), when attempted: builds the day skeleton via `plan_generator._resolve_split`/`_build_day_plans` (reusing those "private" underscore-prefixed functions directly — a real coupling between the two modules), filters the exercise catalog to equipment-compatible candidates, builds a prompt (`_build_prompt`) listing the day skeleton and a compact `slug/name/primary_muscles/equipment`-only catalog, and calls `ai_utils.generate_structured` against Groq's `openai/gpt-oss-120b` model with a JSON-schema-constrained `ProgramBatch` response (`minItems == maxItems == len(day_plans)`, enforced at the schema level after a real incident where the model silently dropped a duplicate-labeled day). It then validates: day count matches; each day is matched **positionally** (not by label — labels legitimately repeat, e.g. two "Push" days in a PPL split) and its label must match; every exercise slug must resolve in the candidate catalog; and a deterministic injury backstop (`_avoided_muscles` / `_INJURY_AVOID_MUSCLE_MAP`) hard-rejects any exercise whose primary muscles intersect an "avoid"-severity injury, independent of whether the LLM honored the prompt's injury instruction (confirmed on a real run that it sometimes doesn't). All of this validation happens **before** any DB write — the function only starts deactivating the old program and inserting rows once validation fully passes, so a validation failure never leaves a half-written program in the session for the fallback to trip over.
6. On success (either path), the response is serialized via `ProgramRead` → Flutter `Program.fromJson` → `ActiveProgramController` state → `plan_overview_screen.dart` / `plan_preview_screen.dart` (module 002) render it.

### (b) Day-editor edit flow (rename day / add muscle tag / fill day)

All three UI actions live in `app/lib/features/programs/presentation/day_editor_screen.dart` and go through the same `ProgramsRepository`, but rename and add-tag share one generic endpoint while fill-day has its own:

- **Rename day**: `_showRenameDialog` (`day_editor_screen.dart:85`) → `ProgramsRepository.updateDay(day.id, {'label': label})` (`programs_repository.dart:125`) → `PATCH /programs/days/{day_id}` → `update_day()` (`programs.py:139`) → `setattr` loop over `ProgramDayUpdate.model_dump(exclude_unset=True)` → `db.commit()` → re-query with explicit `selectinload` (a plain `db.refresh()` only reloads columns, not relationships, and accessing an expired relationship outside the request's greenlet context raises `MissingGreenlet` — the endpoint's own comment documents this) → `ProgramDayRead` response → `ActiveProgramController.refresh()` (`invalidateSelf()` + `await future`) re-fetches the whole active program via `GET /programs/active`.
- **Add muscle tag**: `_showAddMuscleTagSheet` (`day_editor_screen.dart:135`) → same `updateDay(day.id, {'muscle_tags': [...day.muscleTags, muscle]})` → same `PATCH /programs/days/{day_id}` → same `update_day()` endpoint. Remove-tag (`_removeMuscleTag`, `day_editor_screen.dart:263`) is identical, filtered client-side before the PATCH. **There is no dedicated rename or tag endpoint — both ride the one generic day-PATCH.**
- **Fill day**: `_fillWithAi` (`day_editor_screen.dart:194`) → `ProgramsRepository.fillDay(dayId)` (`programs_repository.dart:145`) → `POST /programs/days/{day_id}/fill` → `fill_day()` (`programs.py:170`, a dedicated endpoint) → `plan_generator.fill_day_exercises(db, day, user)` (`plan_generator.py:234`) — **this calls `plan_generator`, not `ai_plan_generator`; it is the same deterministic `select_exercises_for_day` heuristic the non-AI generator uses, and never calls Groq.** It computes `remaining_slots = per_day_count - len(day.exercises)` (target count from `_exercises_per_day(user.session_minutes or day.estimated_minutes)`); if `<= 0` it's a no-op; otherwise it appends (never replaces) newly chosen exercises, commits, `db.expire_all()`s (the pre-loaded `day` object's `exercises` collection wouldn't otherwise reflect the new rows), and re-queries with eager loading before returning.
- Exercise add/edit/remove/reorder (`_AddExerciseSheet`, `_EditExerciseSheet`, `ReorderableListView.onReorder`) follow the same shape: repository call → dedicated `POST/PATCH/DELETE /programs/days/{day_id}/exercises` or `/programs/exercises/{id}` → matching endpoint in `programs.py` → `ActiveProgramController.refresh()`.

## Data / Schema

Backend (`backend/app/models/program.py`, `backend/app/models/exercise.py`):

- `Program`: `id`, `owner_id` (FK `users.id`), `name`, `split_type`, `days_per_week`, `duration_weeks` (default 8), `source` (`"generated"` or `"ai_generated"` — both actually produced; no observed code path writes `"manual"`), `is_active` (default true), `created_at`; `days` relationship (cascade `all, delete-orphan`, ordered by `order_index`).
- `ProgramDay`: `id`, `program_id` (FK), `order_index`, `weekday` (0=Mon..6=Sun, nullable = unscheduled), `label`, `muscle_tags` (JSONB list), `is_rest` (default false), `estimated_minutes` (nullable); `exercises` relationship (cascade delete-orphan, ordered by `order_index`).
- `ProgramExercise`: `id`, `program_day_id` (FK), `exercise_id` (FK `exercises.id`), `order_index`, `sets` (default 3), `rep_range_low`/`rep_range_high` (default 8/12), `load_type` (`weight | percent_1rm | rpe`, default `weight`), `target_value` (nullable float), `tempo` (nullable, `String(16)`), `superset_group` (nullable, `String(8)`), `notes` (nullable, `String(500)`), `coach_with_camera` (default false).
- `Exercise`: `id`, `slug` (unique), `name`, `primary_muscles`/`secondary_muscles`/`equipment` (JSONB lists), `difficulty`, `execution_steps`/`pro_cues` (JSONB lists), `mistakes` (JSONB list of `{title, why, fix}`), `supports_camera` (default false), `camera_view` (nullable, `"front"` or `"side"`), `created_at`. Seeded via `backend/app/db/seed_data.py` — 47 hand-authored exercises (its own docstring says "~45") spanning Chest, Back, Shoulders, Arms, Legs, and Core; explicitly documented as FORMA's own curated set, not a third-party database import.

Pydantic schemas (`backend/app/schemas/program.py`, `backend/app/schemas/exercise.py`) mirror the models. Notably: `ProgramExerciseCreate`/`ProgramExerciseUpdate` place no numeric bounds on `sets`/`rep_range_low`/`rep_range_high`/`target_value`; by contrast the AI-generation-only schema `ProgramExerciseGen` (`ai_plan_generator.py:42`) constrains `sets` to 1–6, `rep_range_low` to 1–60, and `rep_range_high` to 1–90 (the upper bound intentionally covers duration-based holds like a plank, per its field description).

Flutter domain (`app/lib/features/programs/domain/{program,exercise}.dart`) is a straight field-for-field mirror of the `*Read` schemas, plus one derived getter each: `Exercise.muscleSummary` (first 3 muscles, title-cased) and `ProgramExercise.repRangeLabel` (`"$low-$high"`).

## Testing Strategy

No automated tests exist for this module. `app/test/` contains only the default Flutter-template `widget_test.dart` (a boilerplate smoke test unrelated to programs/exercises). The backend `.venv` contains vendored dependency test suites (pytest, sqlalchemy, etc.) but no `backend/tests/` directory or any project-authored test file targeting `plan_generator.py`, `ai_plan_generator.py`, `ai_utils.py`, or the `programs`/`exercises` endpoints was found anywhere in the repository.

This is a meaningful gap given the architecture: the AI-vs-deterministic fallback in `generate_program_smart` is a silent-failure design by construction (any exception is swallowed and retried deterministically, logged only via `logger.warning`) — there is no test exercising "AI call raises → fallback produces a valid program," "AI returns a day-count mismatch → fallback triggers," "AI violates injury-avoidance → fallback triggers," or "GROQ_API_KEY unset → deterministic path used directly." A regression that broke the fallback itself (e.g. the `db.rollback()` + re-fetch dance ai_plan_generator.py documents as fragile) would only surface in production, and only when the AI path also happens to be failing.

## Risks / Edge Cases

- **Silent AI fallback with no user-visible signal.** `generate_program_smart` swallows every AI-path failure and falls back transparently; the resulting `Program.source` (`"generated"` vs `"ai_generated"`) is parsed into the Flutter `Program` model but never read or displayed by any screen in this module (confirmed: no reference to `.source` anywhere in `app/lib/features/programs/` or `app/lib/features/onboarding/` outside the model definition itself). A user cannot tell whether they got an AI-personalized plan or the rule-based fallback.
- **"Let AI fill this day" is not AI.** The day-editor button (`day_editor_screen.dart:393`, labelled "✨ Let AI fill this day") calls `POST /programs/days/{day_id}/fill`, which is wired to `plan_generator.fill_day_exercises` — the same deterministic heuristic as the non-AI generator, with zero Groq/LLM involvement. The repository's own doc comment (`programs_repository.dart:142`) correctly calls it "the backend's plan-builder heuristic," but the UI copy the user actually sees implies AI personalization that doesn't happen for this action (unlike full-program generation, which genuinely does try AI first).
- **Manual edits bypass the AI path's validation bounds.** `ProgramExerciseUpdate`/`ProgramExerciseCreate` have no server-side numeric constraints on sets/reps/target value; the Flutter `_EditExerciseSheet` clamps sets to 1–12 and rep range to 1–30 purely client-side, with its own code comment noting "the persisted value has no such bound enforced server-side." A client that skips the app's UI (or a future bug in it) could write out-of-range values the AI generation path would have rejected by schema.
- **Deterministic exercise selection can under-fill a day.** `select_exercises_for_day` picks at most one exercise per muscle tag; if the catalog has no equipment-compatible candidate for a tag (or a day's `muscle_tags` list is shorter than the target per-day count), the day ends up with fewer exercises than `_exercises_per_day` targets — there is no minimum-count enforcement or error in that case, for either `generate_program` or `fill_day_exercises`.
- **`ai_plan_generator` reaches into `plan_generator`'s "private" functions.** `_resolve_split`, `_build_day_plans`, `_exercises_per_day`, and the `_DayPlan` dataclass (all underscore-prefixed) are imported and called directly from the other module (`ai_plan_generator.py:184-186`) rather than through a public interface — a real coupling that makes the two modules' skeleton logic easy to accidentally desync.
- **"ADD TO PLAN" on the exercise detail screen is inert.** `exercise_detail_screen.dart:264-270` shows a snackbar ("Open a day to add exercises for now") instead of performing any mutation — a known-incomplete affordance, not a dead code path removed elsewhere.
- **Rate-limit-driven prompt trimming is a real constraint, not a style choice.** `_format_exercise_catalog`'s comment and `ai_utils.max_tokens_for`'s comment both cite confirmed incidents (an 8000 TPM cap hit on a real 4-day request; a real silent mid-generation truncation) — the compact-JSON catalog and explicit `max_tokens` sizing exist specifically to avoid those failures recurring, and both failure modes funnel into the same `generate_program_smart` fallback if they happen again.
