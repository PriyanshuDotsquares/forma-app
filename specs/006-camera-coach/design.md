## Approach
Camera-coach is a layered, camera-agnostic pipeline: a thin native platform-channel wrapper (`MediaPipePoseDetector`) feeds raw `Pose` landmarks up to `PoseCoachService`, which owns the `camera` plugin lifecycle and frame plumbing. A mapper (`pose_angle_mapper.dart`, owned by module 005 but the sole bridge between the two) converts `Pose` into camera-agnostic `JointAngles`. From there, two pure, unit-testable state machines — `RepCounter` (hysteresis rep counting) and `FormHeuristics` (weighted deviation-from-ideal-range scoring) — never import `camera` or the pose types at all, so they can be exercised with plain Dart values. `VoiceCoach` wraps `flutter_tts` with a verbosity-based rate limiter. There is no ML-based form classifier anywhere in this pipeline: rep counting is a threshold state machine, and form scoring is a hand-authored, per-movement-pattern rule table scored by linear penalty — both are explicitly documented as heuristics, not trained models (`domain/form_heuristics.dart:161-165`).

## Architecture / Data Flow
1. **Camera capture** — `PoseCoachService.startStream()` (`data/pose_service.dart:167-173`) calls `CameraController.startImageStream(_handleImage)`. Each `CameraImage` is validated (`_frameFor`, `pose_service.dart:225-277`): raw pixel format must match `nv21` (Android, raw code 17) or `bgra8888` (iOS, raw code 1111970369), and there must be exactly 1 plane; otherwise the frame is dropped. `_isBusy` guards against overlapping processing — a frame arriving mid-processing is dropped, not queued (`pose_service.dart:183-211`).
2. **Native pose detection** — the frame's bytes/dimensions/rotation cross a `MethodChannel('forma/pose_landmarker')` via `MediaPipePoseDetector.detect()` (`data/mediapipe/mediapipe_pose_detector.dart:45-76`) to:
   - **iOS**: `ios/Runner/MediaPipePoseChannel.swift` builds a `CVPixelBuffer` directly over the bgra8888 bytes (zero-copy) and calls `PoseLandmarker.detect()` synchronously on a dedicated serial `DispatchQueue`. Landmarks come back relative to the *original, unrotated* buffer and are manually rotated into upright normalized space, then scaled by the upright width/height (`MediaPipePoseChannel.swift:127-161`).
   - **Android**: `android/.../MediaPipePoseChannel.kt` cannot hand MediaPipe's Android `detect()` the raw nv21 bytes — its `AndroidPacketCreator` rejects YUV/NV21 despite an `IMAGE_FORMAT_NV21` constant existing (confirmed via a runtime `UnsupportedOperationException`, per the code comment) — so it first re-encodes nv21 → JPEG (quality 90, via `YuvImage.compressToJpeg`) → `Bitmap`, then rotates the *bitmap itself* upright with a `Matrix` before calling `detect()` on a dedicated single-thread `Executor` (`MediaPipePoseChannel.kt:113-158`).
   - Both platforms use `PoseLandmarkerOptions` with `Delegate.CPU` (no GPU delegate) and `RunningMode.IMAGE`/`.image` (synchronous, one call at a time), backed by the bundled model `assets/models/pose_landmarker_full.task` (~9.4MB, MediaPipe Tasks Vision BlazePose "full" variant; declared as a Flutter asset in `pubspec.yaml:79-83`, pulled in natively via CocoaPod `MediaPipeTasksVision 1.0.0` on iOS (`ios/Podfile:23`) and Gradle `com.google.mediapipe:tasks-vision:1.0.0` on Android (`android/app/build.gradle.kts:50`)).
   - The result (33 BlazePose landmarks with x/y in the upright frame's pixel space, z as relative depth, and a `visibility` score) is mapped index-by-index into `PoseLandmarkType.values` order and wrapped as a `Pose` (`mediapipe_pose_detector.dart:59-76`, `data/mediapipe/pose_types.dart`). A `null` result (no body detected) propagates as `null` all the way up.
3. **Angle extraction** — `jointAnglesFromPose()` (`workout/presentation/widgets/pose_angle_mapper.dart:80-111`) computes the interior angle at elbow/hip/knee from shoulder-elbow-wrist / shoulder-hip-knee / hip-knee-ankle landmark triples using 2D image-plane vector math (`_angleAt`, lines 22-30), averaging left/right sides when both landmarks are ≥0.5 likelihood, plus a self-normalized 0..~1 bar-height proxy from wrist/shoulder/ankle y-coordinates. This is the module boundary: everything downstream only ever sees `JointAngles`.
4. **Per-frame consumption** — `LiveTrackingOverlay._handlePose()` (`workout/presentation/widgets/live_tracking_overlay.dart:122-140`) feeds each frame's `JointAngles` into both:
   - `FormHeuristics.evaluateFrame()` + `.addSample()` (`domain/form_heuristics.dart:198-234`) — evaluates the current `MovementPattern`'s rules (inferred once per set from exercise name/muscles via `inferMovementPattern`, a keyword heuristic, `form_heuristics.dart:13-49`), producing a `FormSnapshot` (active cues + per-joint flags) for immediate UI/voice use, and accumulating a running per-frame score (100 minus each out-of-range rule's weight × linear penalty ramped over 30°, `_scoreFrame`, lines 253-269) into the set's eventual average.
   - `RepCounter.addSample()` (`domain/rep_counter.dart:105-156`) — a two-threshold hysteresis machine keyed to one driving joint per pattern (`repCounterConfigFor`, `pose_angle_mapper.dart:127-150`, e.g. knee for squat, hip for hinge, elbow for press/pull). A rep completes when the value crosses bottom-threshold then back past top-threshold with excursion ≥15°; `onRepCompleted` fires a `RepResult` with rep index, ROM% (excursion ÷ configured threshold gap), and eccentric/concentric split timings.
5. **Rep grading & speech** — on `onRepCompleted` (`live_tracking_overlay.dart:142-154`): `FormHeuristics.repLookedGood` (did every rule's joint reach its ideal range at some point this rep) grades the rep, `markRepBoundary()` resets per-rep tracking, `VoiceCoach.announceRep(index)` speaks the number, and — if the rep wasn't flagged — `VoiceCoach.speakEncouragement('Nice rep')`. Independently, any frame with active cues speaks the first cue via `VoiceCoach.speak()` (rate-limited per verbosity, `data/voice_coach.dart:72-130`).
6. **UI overlay** — `PoseSkeletonPainter` (`workout/presentation/widgets/pose_painter.dart`) draws stick-figure bone segments colored red/green per the current `FormSnapshot`'s flagged-joint booleans, plus blue dots at every ≥0.4-likelihood landmark, scaled independently per axis into the preview's bounds (not a pixel-exact reprojection, per its own doc comment). `LiveTrackingOverlay` also renders a live rep counter, last-rep ROM ring, and the active cue as a red banner.
7. **Set finish & handoff** — `LiveTrackingOverlay._finish()` (`live_tracking_overlay.dart:165-178`) stops the stream and calls `widget.onFinish(LiveSetResult(...))` with total reps, `FormHeuristics.computeScore()` (plain average of every sampled frame's score, 0-100, defaults to 100 if no samples), the *last completed rep's* ROM% only (not a set average), good/bad rep tallies (from a per-rep flagged-or-not list), and `dominantFlaggedJoint`. `ActiveWorkoutScreen._handleLiveSetFinished()` (`workout/presentation/active_workout_screen.dart:459-476`) writes these onto the in-progress `_SetEntry` row as hints (`formScoreHint`, `romHint`, `goodRepsHint`, `badRepsHint`, `flaggedJointHint`) — still editable, not yet persisted.
8. **Persistence (module-005-owned)** — only when the lifter taps "LOG SET" does `ActiveWorkoutScreen._logCurrentSet()` call `WorkoutRepository.logSet(..., formScore: row.formScoreHint, depthPct: row.romHint)` (`active_workout_screen.dart:333-346`), which `POST`s to `/workouts/sessions/{sessionId}/sets` with `form_score`/`depth_pct` alongside the normal weight/reps fields (`workout/data/workout_repository.dart:50-75`). `dominantFlaggedJoint` is used purely client-side to pick a relevant `Exercise.mistakes` entry for the post-set coaching note (`active_workout_screen.dart:294-322`) — it is not itself sent to the backend.
9. **Precheck (separate, lighter use)** — `CameraPrecheckScreen` (`workout/presentation/camera_precheck_screen.dart`) runs its own `PoseCoachService` instance purely to compute framing signals (`_evaluate`, lines 36-78) before the lifter confirms readiness; on confirm it sets `pendingCameraCoachProvider` (a session-id flag) and hands off to `ActiveWorkoutScreen`, which renders `LiveTrackingOverlay` (a *second*, independent `PoseCoachService`/`RepCounter`/`FormHeuristics`/`VoiceCoach` instance) when that provider matches the current session (`active_workout_screen.dart:579-591`).

## Data / Schema
No persisted schema belongs to this module — everything is in-memory, scoped to the life of the screen/widget that created it:
- `Pose` / `PoseLandmark` / `PoseLandmarkType` (`data/mediapipe/pose_types.dart`) — one frame's 33 landmarks (x/y pixel-space, z relative depth, likelihood/visibility 0-1). Discarded after each frame is consumed.
- `JointAngles` (`domain/rep_counter.dart:15-22`) — one frame's derived elbow/hip/knee angles (degrees) + normalized bar height. The sole type `RepCounter`/`FormHeuristics` operate on.
- `RepResult` (`domain/rep_counter.dart:31-58`) — one completed rep's index, ROM%, and eccentric/concentric tempo split. `tempoEccentricSeconds`/`tempoConcentricSeconds` are computed on every rep but never read anywhere outside `rep_counter.dart` itself (not surfaced in `LiveSetResult`, the UI, or persisted) — see Backlog/Known Gaps.
- `FormSnapshot` (`domain/form_heuristics.dart:137-148`) — one frame's active cues + per-joint flags; drives the skeleton painter and the spoken-cue selection each frame, not accumulated.
- `LiveSetResult` (`workout/presentation/widgets/live_tracking_overlay.dart:20-46`) — one set's summary, transient state on `ActiveWorkoutScreen`'s `_SetEntry` row until "LOG SET" is tapped.
- The only data that survives past the screen is the two scalar fields module 005 already persists via the existing `WorkoutSet` model: `formScore` (int?) and `depthPct` (double?, populated from the last rep's ROM%) on `POST /workouts/sessions/{id}/sets` — both are generic fields on that endpoint, not camera-coach-specific columns, and both are optional/nullable (a manually-logged set has neither).

## Testing Strategy
No automated tests exist for this module — a genuine gap. `find app/test` turns up only the default `test/widget_test.dart`; nothing references `RepCounter`, `FormHeuristics`, `PoseCoachService`, `MediaPipePoseDetector`, or `VoiceCoach`. This is especially notable here because `RepCounter` and `FormHeuristics` were deliberately built as pure, camera/ML-Kit-free Dart classes specifically *to be* unit-testable (per `rep_counter.dart:1-8`'s own doc comment on why `JointAngles` exists as a decoupling boundary) — the testability was designed in, but no tests were written against it. There is also no ground-truth fixture data (e.g. a recorded rep sequence with known-good rep counts/form scores) to validate the heuristic's accuracy against, which matters more for this module than most: rep-counting thresholds and ideal-angle ranges are hand-tuned constants with no automated regression protection if they're ever adjusted.

## Risks / Edge Cases
- **Heuristic, not ML-based, form scoring** — explicitly disclaimed in code: "This is a heuristic, not a trained model. It has no ground-truth motion-capture data behind it, doesn't account for individual limb proportions or camera angle, and only looks at 2D joint angles derived from a single camera" (`domain/form_heuristics.dart:161-165`). Ideal ranges are coach-authored rough averages, not measured.
- **Android's nv21→JPEG→Bitmap conversion** (`MediaPipePoseChannel.kt:113-158`) adds a lossy re-encode (quality 90) plus a bitmap rotation on every processed frame — real per-frame CPU/latency cost and a small fidelity loss versus iOS's zero-copy `CVPixelBuffer` path, though frame-dropping under `_isBusy` bounds the worst case.
- **CPU-only inference** (`Delegate.CPU` on both platforms) — no GPU delegate configured, which caps achievable frame-processing rate on lower-end devices; combined with drop-when-busy backpressure, this means "every frame" is never actually guaranteed, especially on Android.
- **Movement-pattern inference is a keyword match**, not a real classifier (`inferMovementPattern`, `form_heuristics.dart:13-49`) — an exercise whose name/muscles don't match any keyword silently falls back to the lenient `generic` pattern (elbow-only, 20-175° — effectively "flag almost nothing").
- **Single camera, single body, 2D angles** — `numPoses = 1` on both platforms; a second person in frame, an occluded joint, or a camera angle that isn't roughly side/front-on all degrade angle accuracy with no compensation.
- **`RepCounter` ignores unavailable-joint frames rather than resetting state** (`rep_counter.dart:105-108`) — a brief occlusion mid-rep doesn't cost the rep, but a *sustained* occlusion (e.g. the lifter stepping fully out of frame at the bottom of a rep) would simply pause the state machine rather than flag anything, and resumes silently once the joint is visible again.
- **`LiveSetResult.romPct` reflects only the last completed rep**, not a set-wide average — a strong final rep can mask a set with several shallow earlier reps in the summary UI.
- **Precheck's "usable pose" thresholds are separate, hand-picked constants** (`poseLooksUsable`'s `minLandmarks: 20`/`minLikelihood: 0.5` in `pose_service.dart:325-329` vs. the precheck screen's own inline `15`/`0.5` in `camera_precheck_screen.dart:39-40`) — two slightly different confidence bars for a similar "is this pose good enough" question, in two different places.

## Backlog / Known Gaps
- `RepResult.tempoEccentricSeconds` / `tempoConcentricSeconds` (`domain/rep_counter.dart:35-36, 53, 57, 141-142`) are computed on every rep but never consumed anywhere outside `rep_counter.dart` — no tempo coaching, display, or persistence exists downstream. Dead output, not a dead code path (the computation runs; nothing reads the result).
- `app/ios/Podfile:1-4`'s comment justifying the `platform :ios, '15.5'` floor still says "google_mlkit_commons (camera pose-coaching) needs 15.5+" — stale: this app has no `google_mlkit_*` dependency anywhere (verified via `pubspec.yaml`/`pubspec.lock`); pose coaching is implemented entirely via the directly-linked `MediaPipeTasksVision` CocoaPod. Likely a leftover comment from an earlier ML-Kit-based prototype that was replaced without updating the rationale text.
- `VoiceCoach.duckMusic` (`data/voice_coach.dart:45-52`) is wired as a pass-through setting with no runtime effect, by explicit design (documented as not attemptable without a fuller audio-session integration) — a real, currently-permanent gap for a lifter playing music during a coached set.
- `AndroidManifest.xml` declares `RECORD_AUDIO` alongside `CAMERA`, but `CameraController` is constructed with `enableAudio: false` everywhere in this module (`data/pose_service.dart:142`) — the permission appears unused by any code this module owns (not confirmed against other features' manifests/plugins that may also require it).
